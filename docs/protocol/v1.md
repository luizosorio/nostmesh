# NostMesh control protocol, version 1

**Status: experimental.** This claims no NIP number and makes no
interoperability promise beyond this implementation. Kinds, tags and field names
may change before any standardization is attempted.

## What this protocol does

It lets two nodes that already know each other's Nostr identity negotiate a
WireGuard tunnel: agree on parameters, exchange ephemeral public keys, and share
connectivity candidates.

It does **not** carry user traffic. Packets go over WireGuard; Nostr carries only
control messages.

## Trust model

Every message is a **proposal, not a command**. A valid signature proves who
composed a message. It does not prove they are honest, and it grants no
authority over the receiving host.

Consequently: `AllowedIPs`, overlay addresses, routes, DNS and firewall rules
are derived from local policy. A field in a received message never configures
the kernel directly.

Relays are untrusted for availability, ordering, confidentiality and retention.
They may duplicate, delay, reorder or drop events, and they see every cleartext
field.

## Envelope

The outer structure, visible to every relay that handles the event:

```json
{
  "v": 1,
  "namespace": "org.nostmesh.experimental",
  "type": "session.request",
  "message_id": "<16 bytes, hex>",
  "session_id": "<32 bytes, hex>",
  "seq": 0,
  "created_at": 1798000000,
  "expires_at": 1798000060,
  "sender": "<nostr pubkey, hex>",
  "recipient": "<nostr pubkey, hex>",
  "reply_to": "<message_id, optional>",
  "body": "<NIP-44 ciphertext>",
  "critical": []
}
```

Everything sensitive — candidates, overlay addresses, WireGuard public keys,
negotiated parameters — lives in the encrypted `body`. The envelope carries only
what routing and validation need.

### Why these fields are in the clear

A relay must be able to deliver a message without decrypting it, which requires
`recipient` at minimum. The rest are here because validation must reject a
message *before* spending CPU on decryption; a version check that required
decrypting first would let any peer make us do expensive work with garbage.

The cost is that a relay observes who talks to whom, when, and how often. This
is documented rather than solved. Connecting to relays over Tor reduces IP
exposure but does not hide the pubkeys.

## Binding cleartext to ciphertext

The cleartext fields are authenticated alongside the encrypted payload. Without
this, a relay could take a valid message and re-address it — changing
`recipient` or `session_id` while the payload stayed intact and decryptable.

NIP-44 does not accept associated data, so the binding is constructed:

1. The sender computes a length-prefixed encoding of the authenticated fields
   (`AssociatedData`), hashes it, and includes the digest in the plaintext
   before encrypting.
2. The receiver recomputes the digest from the envelope **as received** and
   compares.

Any alteration to `v`, `namespace`, `type`, `message_id`, `session_id`, `seq`,
`created_at`, `expires_at`, `sender`, `recipient` or `critical` produces a
different digest, and the message is refused.

The encoding is length-prefixed so no two distinct field sets can produce
identical bytes.

## Validation order

Cheapest first, and this ordering is a defence rather than a style choice. Each
step costs more than the last, and an attacker who can make a node decrypt
garbage costs it far more than one who can make it compare two integers.

| Step | Check | Cost |
|---:|---|---|
| 1 | Frame size | length comparison |
| 2 | JSON depth, strict parse, unknown fields rejected | linear scan |
| 3 | Version and namespace | integer and string comparison |
| 4 | Message type in the known set | map lookup |
| 5 | Critical extensions understood | slice scan |
| 6 | Field shapes, sizes, encodings | per-field |
| 7 | Recipient is this node | comparison |
| 8 | Validity window against the local clock | arithmetic |
| 9 | Nostr event id and signature | **cryptographic** |
| 10 | Rate limit | per-sender state |
| 11 | Decrypt and verify the context binding | **cryptographic** |
| 12 | Payload schema, nonce, sequence, state machine | per-message |
| 13 | Local policy | policy engine |
| 14 | Network effects | kernel |

Steps 1–8 and 11–12 are implemented in `internal/protocol`. Steps 9–10 belong to
the transport, and 13–14 to the orchestrator.

## Message types

| Type | Seq | Purpose |
|---|---:|---|
| `session.request` | 0 | Open a session, declare capabilities |
| `session.offer` | 0 | Conditionally accept, commit parameters |
| `session.accept` | 1 | Accept the offer's exact hash |
| `candidate.update` | n | Add or remove connectivity candidates |
| `session.ready` | n | Report local tunnel confirmation |
| `session.keepalive` | n | Refresh control-plane liveness |
| `session.close` | n | End with a stable reason |
| `session.error` | n | Report a sanitized failure |

`session.ready` is **informative**. A session becomes established when this node
verifies the tunnel itself. A peer saying it is ready is not evidence about the
local host.

## Tunnel keys

Only the **public** WireGuard key ever appears in signaling, inside the
encrypted payload, bound to:

```
session_id · sender · recipient · nonce · expires_at
```

The private key never leaves the node that generated it — not in an event, a
log, the network journal, or a diagnostic bundle. This is enforced by the type
system (NM-06) and by an architecture test that fails the build if any
serialized structure declares a private-key field.

A public key on its own is 32 bytes that say nothing about who vouched for it,
for which session, or for how long. The binding is what makes it an
authorization. Replaying one into a different session fails because the
`session_id` is in the authenticated context.

Each session generates an independent key pair. A key never carries across
sessions, and a closed session never reopens.

## Capability negotiation

Both sides declare what they support; the offer commits to the intersection and
is hashed. The acceptance references that hash rather than restating terms, so
modified terms cannot be accepted by replaying an earlier acceptance.

A peer claiming agreement on a version this build never offered is refused as a
downgrade attempt.

**Critical extensions**: a sender may mark an extension essential. A receiver
that does not understand one **must refuse the message**. Processing it with the
extension ignored would mean processing something other than what was sent.
Version 1 defines no extensions, so any critical extension is currently refused.

## Cryptography

**NIP-44 v2** for directed encryption, **secp256k1 Schnorr** for event
signatures, per NM-10. No cryptography is invented here; the implementation is
verified against the official NIP-44 vectors.

### Forward secrecy: absent

NIP-44 derives its conversation key from the two long-term identity keys. That
key is therefore stable for a given pair, and **a compromised Nostr private key
allows decryption of any historical signaling a relay retained**.

What that would reveal: endpoints, candidates, negotiated routes, overlay
addresses, and historical **public** WireGuard keys.

What it would not reveal: any WireGuard **private** key, since none is ever
transmitted.

Mitigations, none of which is a substitute for forward secrecy:

- short validity windows, so retained events age out of usefulness
- minimal metadata in both the envelope and the payload
- ephemeral tunnel keys that are never derived from the conversation key
- identity rotation, supported by the version and revocation fields

A session protocol with forward secrecy remains possible. It would be a new
protocol version, not a change to this one.

### Post-compromise recovery

Rotating the Nostr identity restores confidentiality for future messages, since
the conversation key derives from it. It does nothing for messages already
retained by a relay.

## Replay and ordering

- `message_id` is random per message, for deduplication across relays that each
  deliver a copy.
- `session_id` is random per session and never reused.
- `seq` orders messages within a session. **Ordering never comes from
  timestamps**: two hosts do not share a clock, and a wrong clock on either side
  must not be able to reorder a session.
- Timestamps decide only whether a message falls inside its validity window,
  with tolerance for clock skew.
- An identical repeated message is idempotent. Different content at the same
  `seq` ends the session: one of the two is not what it claims to be.

## Error handling

Error codes are a closed, coarse set: `unsupported_version`, `unauthorized`,
`malformed`, `expired`, `replay`, `unsupported_capability`, `internal`.

They are coarse deliberately. A precise error tells an attacker which of their
guesses was closer; the detail belongs in local logs. For the same reason,
decryption failures do not distinguish a wrong key from a failed authentication
tag — either distinction is an oracle.

## Privacy of tags

The outer Nostr event carries the minimum tags needed for a relay to deliver it
to the recipient. It does **not** expose candidates, overlay addresses,
WireGuard keys, routes or negotiated parameters.

An observer of a relay still learns: which pubkeys exchange messages, when, how
often, and roughly how large the messages are.

## Event kind

Development uses kind **31111**, in the parameterized-replaceable range. This is
provisional and deliberately unclaimed: a final kind requires interoperability
review and coordination that this project has not done.

## Limits

| Limit | Value | Reason |
|---|---:|---|
| Envelope size | 64 KiB | Bounds parse cost |
| Payload size | 32 KiB | Bounds decryption cost |
| JSON depth | 16 | Bounds recursion |
| Critical extensions | 8 | Bounds the scan |
| Candidates per update | 32 | Bounds candidate processing |
| Clock skew tolerance | 5 min | Hosts are not synchronized |
| Validity window | 10 min | Limits the value of a retained event |

## Test vectors

`internal/protocol/testdata/envelopes.json` holds golden vectors covering both
valid envelopes and every rejection reason. They carry no real key material:
keys and identifiers are derived from visible seeds.

Regenerate with `UPDATE_GOLDEN=1 go test ./internal/protocol/` after a
deliberate format change, and review the diff — that diff *is* the compatibility
break.
